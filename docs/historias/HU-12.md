## Historia

**Como** solicitante **quiero** ver el detalle de mi caso y la solución registrada **para** saber cómo se resolvió.

## Reglas de negocio

1. El detalle muestra los datos del caso (tipo, título, descripción, área, categoría, prioridad, estado y fechas de creación, asignación y cierre), el solicitante, el agente responsable, las atenciones (diagnóstico, solución, agente y fecha) y el historial.
2. El **solicitante solo ve sus casos** (RN-05). Un caso ajeno responde `404`, igual que un caso inexistente (D-17). Agente, validador y administrador ven cualquiera.
3. Quien consulta envía su `usuario_id`, que debe existir y estar activo.
4. Es de solo lectura.

## Criterios de aceptación

- **E1:** *Given* un caso propio cerrado, *When* el solicitante abre el detalle, *Then* ve la solución registrada, el agente y el historial.
- **E2:** *Given* un caso ajeno, *When* el solicitante intenta abrir el detalle (por API o cambiando la URL), *Then* la API responde `404` y la pantalla muestra "Caso no encontrado".
- **E3:** *Given* un caso propio sin atenciones, *When* abre el detalle, *Then* ve los datos y el mensaje "Aún no hay atenciones registradas".

## Excepciones

| Situación | Respuesta |
|---|---|
| El caso no existe o es ajeno para el solicitante | `404` |
| `id` o `usuario_id` no son enteros positivos | `400` |
| El usuario no existe o está inactivo | `400` |
| Error de la base de datos | `500` |

## Diseño

**API:** `GET /api/casos/:id?usuario_id=1` → `200` con los campos de la fila de HU-02, más `descripcion`, `fecha_asignacion`, `fecha_cierre` y `atenciones` (con la misma forma que `GET /api/casos/:id/atenciones`, en orden cronológico). El historial se sigue pidiendo a `GET /api/casos/:id/historial`.

**Pantalla:** `/mis-solicitudes/:id`, con un botón **Ver detalle** en cada fila de Mis Solicitudes. Muestra los datos del caso con los badges existentes, las atenciones y la línea de tiempo `HistorialTimeline` de HU-08. Botón **Volver**.
