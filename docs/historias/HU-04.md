## Historia

**Como** agente **quiero** asignarme un caso **para** asumir su atención.

## Reglas de negocio

1. El agente se asigna el caso **a sí mismo**: el `usuario_id` que envía es el agente que queda como responsable. Debe existir, estar activo y tener rol `agente`.
2. Solo se asigna un caso **sin agente** que esté `Pendiente` o `En análisis`.
3. Al asignar se guardan `agente_id` y `fecha_asignacion` (la fecha la pone el backend).
4. **Si el caso está `Pendiente`, pasa a `En análisis`** ([D-14](../decisiones.md)). Si ya está `En análisis`, el estado no cambia.
5. Se registra **un** evento `asignacion` en `historial`, con el estado anterior y el nuevo (iguales si no cambió), en la misma transacción que el `UPDATE`. El caso se lee con `SELECT … FOR UPDATE` para que dos agentes no se lo asignen a la vez.
6. **Se agrega a HU-05:** para pasar a `En atención` con `PATCH /api/casos/:id/estado`, el caso debe tener agente asignado.
7. No se puede reasignar ni quitar el agente (fuera del alcance del MVP).

## Criterios de aceptación

- **E1 (CP-06):** *Given* un caso `Pendiente` sin agente, *When* el agente pulsa "Asignarme", *Then* queda como responsable con `fecha_asignacion`, el caso pasa a `En análisis` y el historial registra `asignacion`.
- **E2:** *Given* un caso ya asignado a otro agente, *When* intenta asignárselo, *Then* el sistema lo impide (`409`) y no cambia nada.
- **E3:** *Given* un caso `En análisis` sin agente, *When* el agente se lo asigna, *Then* queda como responsable y el estado sigue `En análisis`.
- **E4:** *Given* un caso `En análisis` sin agente, *When* se intenta pasar a `En atención`, *Then* el sistema lo impide (`409`).
- **E5:** *Given* la bandeja, *When* el agente la abre, *Then* el botón "Asignarme" solo aparece en los casos sin agente que están `Pendiente` o `En análisis`.

## Excepciones

| Situación | Respuesta |
|---|---|
| El caso no existe | `404` |
| `id` o `usuario_id` no son enteros positivos | `400` |
| El usuario no existe, está inactivo o no es agente | `400` |
| El caso ya tiene agente | `409` |
| El caso está `En atención`, `En validación` o `Cerrada` | `409` |
| Dos agentes se asignan el mismo caso a la vez | Uno recibe `200` y el otro `409`; queda un solo evento |
| Error de la base de datos | `500` y *rollback* |

## Diseño

**API:** `PATCH /api/casos/:id/asignar`

```json
{ "usuario_id": 3 }
```

La respuesta `200` devuelve el caso actualizado, con la misma forma que `PATCH /api/casos/:id/estado`. La lógica va en `services/estados.js` o en un servicio que lo use, para que la regla 6 viva junto a la máquina de estados.

**Seeds:** se corrigen los eventos de los casos 3 a 6 para que cumplan la máquina de estados (D-14):
- Casos 4, 5 y 6: `asignacion` `Pendiente → En análisis`, seguido de `cambio_estado` `En análisis → En atención`.
- Caso 3: `asignacion` `En análisis → En análisis`, seguido de `cambio_estado` `En análisis → En atención`.

**Pantalla:** en `/bandeja-soporte`, botón **Asignarme** en la columna de acción, para los casos que cumplen E5. Al pulsarlo se recarga la bandeja y la fila muestra el agente y su siguiente acción. Si el backend lo rechaza, se muestra su `error` en la fila, como en HU-05.

## Decisiones del refinement

| # | Pregunta | Decisión |

| R1 | ¿Asignarse mueve el caso de `Pendiente` a `En análisis`? | **Sí** (D-14, Sprint 2 Planning). |
