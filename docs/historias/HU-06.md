## Historia

**Como** agente asignado **quiero** registrar el diagnóstico y la solución de un caso **para** dejar constancia de lo que hice y enviarlo a validación.

## Reglas de negocio

1. Solo el **agente asignado** al caso registra la atención: el `usuario_id` debe existir, estar activo, tener rol `agente` y ser el `agente_id` del caso.
2. Solo se registra atención en un caso `En atención`.
3. El **diagnóstico es obligatorio** (al menos 10 caracteres). La **solución es opcional**: un agente puede dejar un diagnóstico parcial y volver más tarde con la solución. Si se envía, también tiene al menos 10 caracteres.
4. Un caso puede tener **varias atenciones** (por ejemplo, una después de cada devolución). La fecha la pone el backend.
5. Registrar una atención **no cambia el estado**. Se guarda en `atencion` y se registra el evento `atencion` en `historial` (estado anterior y nuevo `En atención`), en la misma transacción ([D-15](../decisiones.md)).
6. **Se agrega a HU-05:** para pasar de `En atención` a `En validación` con `PATCH /api/casos/:id/estado`, el caso debe tener **al menos una atención con solución**. Ese paso se registra con el evento `envio_validacion` (el que ya usan los seeds), no con `cambio_estado`.
7. Las atenciones de un caso se consultan con `GET /api/casos/:id/atenciones`, que usan el agente (HU-06) y el validador (HU-07).

## Criterios de aceptación

- **E1 (CP-07):** *Given* un caso `En atención` asignado al agente, *When* registra diagnóstico y solución, *Then* la atención queda guardada con su fecha y su agente, y el historial registra `atencion`.
- **E2:** *Given* un caso asignado a otro agente, *When* el agente intenta registrar una atención, *Then* el sistema lo impide (`409`).
- **E3:** *Given* el formulario, *When* el diagnóstico está vacío o tiene menos de 10 caracteres, *Then* el sistema lo rechaza (`400`) y no guarda nada.
- **E4:** *Given* un caso `En atención` cuya única atención no tiene solución, *When* se intenta pasar a `En validación`, *Then* el sistema lo impide (`409`).
- **E5:** *Given* un caso con una atención con solución, *When* el agente lo pasa a `En validación`, *Then* el cambio se guarda y el historial registra `envio_validacion`.

## Excepciones

| Situación | Respuesta |
|---|---|
| El caso no existe | `404` |
| `id` o `usuario_id` no son enteros positivos | `400` |
| El usuario no existe, está inactivo o no es agente | `400` |
| Diagnóstico ausente o con menos de 10 caracteres; solución con menos de 10 caracteres | `400` con un elemento en `detalles` por fallo |
| El usuario no es el agente asignado | `409` |
| El caso no está `En atención` | `409` |
| `En atención → En validación` sin atención con solución | `409` |
| Error de la base de datos | `500` y *rollback* |

## Diseño

**API:**

`POST /api/casos/:id/atenciones` → `201` con la atención creada.

```json
{
  "usuario_id": 3,
  "diagnostico": "La fuente de poder está defectuosa.",
  "solucion": "Se reemplazó la fuente y el equipo enciende normalmente."
}
```

`GET /api/casos/:id/atenciones` → `200` con la lista ordenada por fecha ascendente:

```json
[
  { "id": 2, "caso_id": 4, "diagnostico": "Bandeja llena y regla de reenvío mal configurada.", "solucion": "Se liberó cuota y se corrigió la regla; …", "fecha": "2026-10-06T11:00:00", "agente_id": 4, "agente": "María Prieto" }
]
```

**Pantalla:** en `/bandeja-soporte`, botón **Registrar atención** en las filas `En atención` asignadas al agente actual. Abre un formulario (en la fila o en un modal) con diagnóstico y solución, que muestra las atenciones previas del caso. Al guardar se recarga la bandeja. El botón "Pasar a En validación" de HU-05 sigue igual; si el backend lo rechaza, se muestra su `error`.

## Decisiones del refinement

| # | Pregunta | Decisión |
|---|---|---|
| R1 | La issue pide diagnóstico y solución obligatorios. ¿Lo son los dos? | **Solo el diagnóstico.** El esquema (`solucion NULL`), los seeds (el caso 3 tiene un diagnóstico sin solución) y la regla "no se pasa a En validación sin una atención con solución" suponen que la solución puede faltar. **Confirmado con el equipo el 2026-10-11.** |
| R2 | ¿Registrar la atención pasa el caso a `En validación`? | **No.** El paso lo hace el agente con HU-05, y el backend exige una atención con solución (regla 6). |
| R3 | ¿Registrar una atención deja historial? | **Sí**, con el nuevo evento `atencion` (D-15), para que HU-08 muestre el trabajo del agente. |
| R4 | ¿Qué evento deja `En atención → En validación`? | `envio_validacion`, como en los seeds y el catálogo de D-08. |
| R5 | ¿Dónde va el formulario si no hay detalle (HU-12)? | En la bandeja, como los controles de HU-05. |
