## Historia

**Como** solicitante **quiero** registrar un incidente o una solicitud de servicio tecnológico **para** pedir atención a la mesa de servicios.

## Reglas de negocio

1. El **tipo** es obligatorio: `Incidente` (interrupción o degradación de un servicio) o `Solicitud` (petición de una acción o servicio).
2. El **área** es obligatoria y debe estar activa. La **categoría** es obligatoria, debe estar activa y **pertenecer al área** elegida.
3. El **título** es obligatorio: de 1 a 150 caracteres sin contar espacios al inicio y al final.
4. La **descripción** es obligatoria: al menos **10 caracteres** sin contar espacios al inicio y al final.
5. La **prioridad** es obligatoria: `P1` (urgente), `P2` (normal) o `P3` (baja).
6. El **solicitante** es el usuario de prueba seleccionado (`usuario_id`). Debe existir, estar activo y tener rol `solicitante`.
7. La fecha de creación la asigna la base de datos y el estado inicial es siempre `Pendiente`. El cliente no puede enviar ninguno de los dos.
8. Se inserta el caso y un evento `creacion` en `historial` **en la misma transacción**. Si falla una de las dos inserciones, no queda ninguna.
9. Todas las validaciones se hacen en el **backend**. El formulario valida solo para mejorar la experiencia.

## Criterios de aceptación

- **E1 (CP-01):** *Given* un solicitante con todos los campos válidos, *When* guarda, *Then* se crea el caso con un ID, queda persistido en MySQL y aparece en la bandeja del agente como `Pendiente`.
- **E2 (CP-02):** *Given* una descripción vacía o de menos de 10 caracteres, *When* guarda, *Then* el sistema rechaza el registro con un mensaje y no se crea ninguna fila.
- **E3 (CP-03):** *Given* el tipo `Solicitud`, *When* guarda, *Then* el caso queda almacenado con tipo `Solicitud`.
- **E4:** *Given* una categoría que no pertenece al área elegida, *When* guarda, *Then* el sistema rechaza el registro.
- **E5:** *Given* un caso registrado, *When* se reinicia la aplicación (backend y MySQL), *Then* el caso sigue existiendo.
- **E6:** *Given* un caso registrado, *When* se consulta su historial, *Then* existe un evento `creacion` con estado nuevo `Pendiente` y el `usuario_id` del solicitante.

## Excepciones

| Situación | Respuesta |
|---|---|
| Falta un campo obligatorio, o tiene un valor fuera de su lista (tipo, prioridad) | `400` con un elemento en `detalles` por cada campo inválido |
| Descripción de menos de 10 caracteres o título de más de 150 | `400` |
| La categoría no pertenece al área, o el área o la categoría están inactivas o no existen | `400` |
| El usuario no existe, está inactivo o no es solicitante | `400` |
| Error inesperado de la base de datos | `500` y no se crea nada (*rollback*) |

## Diseño

**API:** `POST /api/casos`

```json
{
  "tipo": "Incidente",
  "area_id": 3,
  "categoria_id": 8,
  "titulo": "Sin Wi-Fi en la biblioteca",
  "descripcion": "No conecta desde las 8:00 en el segundo piso.",
  "prioridad": "P1",
  "usuario_id": 1
}
```

La respuesta `201` devuelve el caso creado con `id`, `estado: "Pendiente"` y `fecha_creacion`.

Si los datos son inválidos, la respuesta es `400`:

```json
{ "error": "Datos inválidos", "detalles": ["La descripción debe tener al menos 10 caracteres"] }
```

**Pantalla:** `/crear-caso` (`CrearCaso.tsx`), en el menú del solicitante.
- Radio Incidente / Solicitud.
- Selects dependientes área → categoría, que cargan `GET /api/areas` y `GET /api/categorias?area_id=`.
- Prioridad, título y descripción, con un contador que avisa si hay menos de 10 caracteres.
- Al guardar muestra el ID creado. Si el backend rechaza, muestra sus `detalles`.
- El `usuario_id` sale de `useUsuario()`.

## Decisiones del refinement

| # | Pregunta | Decisión |
|---|---|---|
| R1 | ¿Se envía `area_id` si la categoría ya implica el área? | **Sí.** El backend lo usa para validar la regla 2 y devolver un error claro. |
| R2 | ¿Qué valor de `evento` se guarda en `historial`? | `creacion`, en minúsculas, como en `seeds.sql` (ver D-08 en `docs/decisiones.md`). |
| R3 | ¿Quién puede registrar casos? | Solo el rol `solicitante`. Se valida en el backend con el `usuario_id`. |
| R4 | ¿Se aceptan áreas o categorías desactivadas? | **No.** HU-11 permite desactivarlas, así que deben dejar de ofrecerse y de aceptarse. |
