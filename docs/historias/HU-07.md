## Historia

**Como** validador **quiero** aprobar o devolver la solución de un caso **para** cerrarlo solo cuando el problema esté resuelto.

## Reglas de negocio

1. Quien valida debe existir, estar activo y tener rol `validador`.
2. Solo se valida un caso `En validación`.
3. **Aprobar:** el caso pasa a `Cerrada` y se guarda `fecha_cierre` (la pone el backend). Evento `cierre` en `historial`.
4. **Devolver:** el caso vuelve a `En atención`, **conserva su agente** y el motivo queda en `historial.detalle`. Evento `devolucion`. El motivo es obligatorio (al menos 10 caracteres).
5. Esta es la **única forma** de llegar a `Cerrada` y de devolver un caso (RN-08). El endpoint genérico de HU-05 sigue rechazándolas.
6. El `UPDATE` del caso y el `INSERT` en `historial` van en la misma transacción, con el caso leído con `SELECT … FOR UPDATE`.
7. Un caso `Cerrada` no cambia (RN-09).
8. Para listar los casos por validar, `GET /api/casos` acepta el filtro `estado=`, combinable con los demás. HU-09 lo reutiliza.

## Criterios de aceptación

- **E1 (CP-09):** *Given* un caso `En validación`, *When* el validador lo aprueba, *Then* queda `Cerrada` con `fecha_cierre` y el historial registra `cierre`.
- **E2 (CP-08):** *Given* un caso `En validación`, *When* el validador lo devuelve con un motivo, *Then* vuelve a `En atención` con el mismo agente y el historial registra `devolucion` con el motivo.
- **E3:** *Given* la devolución, *When* el motivo está vacío o es muy corto, *Then* el sistema lo rechaza (`400`) y el caso no cambia.
- **E4:** *Given* un caso que no está `En validación`, *When* se intenta validar, *Then* el sistema lo impide (`409`).
- **E5:** *Given* la pantalla Por validar, *When* el validador la abre, *Then* ve solo los casos `En validación`, con la solución registrada por el agente.

## Excepciones

| Situación | Respuesta |
|---|---|
| El caso no existe | `404` |
| `id` o `usuario_id` no son enteros positivos | `400` |
| El usuario no existe, está inactivo o no es validador | `400` |
| `accion` distinta de `aprobar` o `devolver` | `400` |
| Devolver sin motivo o con menos de 10 caracteres | `400` |
| El caso no está `En validación` (incluido `Cerrada`) | `409` |
| `estado=` con un valor que no es un estado válido | `400` |
| Error de la base de datos | `500` y *rollback* |

## Diseño

**API:** `POST /api/casos/:id/validacion` → `200` con el caso actualizado.

```json
{ "usuario_id": 5, "accion": "devolver", "motivo": "El proyector sigue sin señal en el aula 201." }
```

```json
{ "usuario_id": 5, "accion": "aprobar" }
```

Al aprobar, `motivo` es opcional y, si llega, se guarda en `detalle`.

**Listado:** `GET /api/casos?estado=En validación` (URL codificada: `estado=En%20validaci%C3%B3n`).

**Pantalla:** `/por-validar` (hoy es un marcador de posición). Lista los casos `En validación` con su título, categoría, agente y la última solución (`GET /api/casos/:id/atenciones`). Cada fila tiene **Aprobar** y **Devolver**; Devolver pide el motivo antes de enviar. Al terminar se recarga la lista.
